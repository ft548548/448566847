## 0 阅读指南

### 0.1 目的与范围

本文是实训平台对外**唯一**的身份与接入依据。接入方读完本文即可完成「拿到账号 → 换取凭证 → 调通接口 → 与考试平台互认 → 通过验收」的全过程。

| 本文覆盖                                     | 本文不覆盖              | 去哪里看                           |
| -------------------------------------------- | ----------------------- | ---------------------------------- |
| 统一身份认证、`sub` 映射、凭证生命周期       | 接口参数的机器可读定义  | `openapi.yaml`（23 个接口）        |
| 网关接入方式、可信头、签名、限流与超时       | 跨平台事件的完整 schema | `event-envelope.yaml`、DV-11       |
| 接口约定、信封互操作、错误码双向映射         | 部署与托管平台限制      | `deployment-vercel.md`             |
| 与考试平台的数据交互规则、准入回源、事件消费 | 公共实体字段级映射      | `data-dictionary-mapping.md`       |
| 异常处理机制、降级、死信与排障               | 偏离的完整理由与补偿    | `deviations.md`                    |
| 权限点与角色、数据归属校验                   | 考试平台内部实现        | 《考试平台接入说明》V1.0 第 5–7 章 |

**本文解决什么问题。** 实训平台目前是一个能独立跑通的系统：DooTask 自建账号体系，登录签发自研凭证，所有接口直接暴露在 PHP 进程端口上。接入统一网关、与考试平台互认之后，会同时出现四个变化：

1. **入口变了。** 用户不再直连应用端口，而是访问网关域名；上游端口只允许网关访问，直连要被拒。
2. **身份变了。** 凭证由论坛身份中心签发，实训平台不再自签浏览器可读的长期凭证；平台内 `userid` 必须能追溯到论坛 `sub`。
3. **协作变了。** 项目准入不再由平台自己判断，而是回源考试平台 `/admissions` 取权威结论；考试结果通过事件回流。
4. **契约变了。** 实训平台是 RPC 风格路径 + `ret` 信封，考试平台是 REST 风格路径 + `code` 信封。两侧必须有一套明确的互操作规则，否则联调时会各自"以为对方懂了"。

前三条决定改造范围，第四条决定本文第 6 章必须写多细。

## 1 接入总览

### 1.1 实训平台在五平台中的位置

| 维度       | 本平台承担的内容                                                                 |
| ---------- | -------------------------------------------------------------------------------- |
| 平台编码   | `workshop`（网关路径段、事件 `sourcePlatform`、`X-App-Code` 三处均用此值）       |
| 权威数据   | 项目与任务、项目成员、招募与报名、文件、项目动态日志                             |
| 下游可消费 | 项目列表与详情、招募列表、成员名单、项目完成状态                                 |
| 上游依赖   | 论坛身份中心（身份与角色）、统一网关（鉴权与路由）、**考试平台（项目准入资格）** |
| 被谁消费   | 成长档案（项目参与记录）、考试平台（项目制学习场景，二期）                       |

### 1.2 参与角色与职责

| 角色         | 职责                                                         | 明确不做                                       |
| ------------ | ------------------------------------------------------------ | ---------------------------------------------- |
| 统一网关     | TLS、路由、令牌校验、限流、可信头注入与伪造头剥离、requestId | 不判断"这个学生能不能进这个项目"               |
| 本平台应用   | 校验可信头与内部签名、执行权限点与数据归属、返回信封         | 不实现授权端点、不签发身份令牌、不解析论坛令牌 |
| 论坛身份中心 | 登录页、授权码、令牌签发、自省、吊销、角色权威               | 不感知项目与考试业务                           |
| 考试平台     | 准入资格权威源、`exam.passed` / `exam.failed` 事件生产方     | 不判断项目分配、不写本平台数据                 |
| 自学平台     | 课程完成状态权威源、`course.completed` 事件生产方            | 不判断考试与项目资格                           |

**边界一句话**：准入的**结论**由考试平台给，准入的**用途**（谁可以进哪个项目）由实训平台定。两者不得互相渗漏——本平台不自行推算"学生学没学完"，考试平台也不判断"这个项目要不要这门课"。

### 1.3 与考试平台的对接范围

这是 V3.0 的核心新增内容。对接不是"接个接口"，而是四条独立的交互通道，每条的责任方、失败影响、数据级别都不同。

#### 1.3.1 四个交互方向

| #   | 方向                | 内容                               | 载体                                              | 发起方   | 同步性 | 失败影响                   |
| --- | ------------------- | ---------------------------------- | ------------------------------------------------- | -------- | ------ | -------------------------- |
| 1   | 实训平台 ← 考试平台 | 课程准入资格查询                   | `GET /api/v1/exam/admissions/{userId}/{courseId}` | 本平台   | 同步   | 无法判定准入，返回"待定"   |
| 2   | 实训平台 ← 考试平台 | `exam.passed` / `exam.failed` 事件 | 事件代理                                          | 考试平台 | 异步   | 准入投影延迟，不影响正确性 |
| 3   | 实训平台 → 考试平台 | 发放准入资格（可选，二期）         | `POST /api/v1/exam/internal/admissions`           | 本平台   | 同步   | 报名即授权场景不可用       |
| 4   | 实训平台 → 考试平台 | 项目完成回流（二期）               | 事件 `project.completed`（目录待登记）            | 本平台   | 异步   | 考试平台无法感知项目制学习 |

**只有这四条，不再长出第五条。** 常见越界是"实训平台直接读考试平台的题库表来渲染项目要求"，或"考试平台直接读项目成员表来决定谁能考试"。这两类需求必须走公开接口或事件，不得直连对方数据库。

#### 1.3.2 准入概念的对齐

两侧对"准入"的建模不同，必须先对齐语义再谈字段。

| 概念       | 考试平台                          | 实训平台                      | 对齐方式                                 |
| ---------- | --------------------------------- | ----------------------------- | ---------------------------------------- |
| 准入主体   | `userId`（= `sub`）               | `userid`（bigint）            | 经绑定表映射，见 4.1、8.2                |
| 准入客体   | `courseId`（如 `course_9`）       | 无课程概念                    | 招募单新增 `course_id`，空表示不校验准入 |
| 准入结论   | `eligible` + `reason`（6 个枚举） | 报名单状态 `pending/approved` | 回源结论作为 `review/apply` 的前置条件   |
| 准入有效期 | 由 `grantedAt` + 规则版本决定     | 本地缓存 60 秒                | 缓存仅加速，不作拒绝依据，见 8.3         |
| 违规约束   | `violationCount`，>3 不通过       | 无                            | 只透传展示，不在本平台二次判定           |

**本平台不新增"准入"业务对象。** 准入是报名审批的输入条件，不是一个独立实体。这一点与考试平台不同（后者有 `admission` 表与 `admissionId`），对接时不要试图对齐表结构。

#### 1.3.3 责任边界

| 事项                   | 实训平台       | 考试平台     | 说明                                   |
| ---------------------- | -------------- | ------------ | -------------------------------------- |
| 判定"课程是否学完"     | 不判定，回源   | 回源自学平台 | 两侧都不自己算                         |
| 判定"考试是否通过"     | 不判定，读结论 | 权威         | —                                      |
| 判定"该学生能否进项目" | **权威**       | 不参与       | 本平台结合准入结论 + 项目规则决定      |
| 发放准入资格           | 可请求（二期） | 权威         | 二期走 `/internal/admissions` + 幂等键 |
| 项目成员增删           | **权威**       | 不参与       | —                                      |
| 成绩与错题             | 只读展示       | 权威         | 本平台不落库，仅缓存展示               |

### 1.4 接入后的四条链路

| #   | 链路       | 路径                                                                                                 | 本平台的责任点                                             |
| --- | ---------- | ---------------------------------------------------------------------------------------------------- | ---------------------------------------------------------- |
| L1  | 用户登录   | 浏览器 → 网关 `/api/v1/workshop/auth/login` → 身份中心 `/oauth/authorize` → 回跳回调 → 换码 → 建会话 | 提供回调路由、校验 state、服务端换码、下发 HttpOnly Cookie |
| L2  | 业务调用   | 浏览器（仅会话 Cookie）→ 网关 → 本平台 `/api/{module}/{method}`                                      | 校验可信头与内部签名、执行权限点与数据归属、返回信封       |
| L3  | 跨平台查询 | 本平台 → 网关 → `GET /api/v1/exam/admissions/{userId}/{courseId}`                                    | L2 签名调用，取权威准入结论，只读不回写                    |
| L4  | 事件       | 事件代理 → 本平台消费 → 更新准入投影                                                                 | 按 `eventId` 幂等、投影只加速不拒绝                        |

### 1.5 关键结论

**结论一　`sub` 映射是本次第一块基石。** 实训平台主键是 `bigint` 自增，论坛 `sub` 是不透明字符串。两者不可互相转换，必须建绑定表。任何"用邮箱拼 ID""用学号当 sub"的做法都会在跨平台查询时炸掉（4.1、8.2）。

**结论二　凭证机制要换，但业务接口不用改。** 现有 `token` 头机制依赖 `base64(userid#$email#$encrypt#$ts#$rnd)`，服务端查库比对 `encrypt`。目标形态改为网关校验论坛令牌 + 注入可信头，业务侧只认 `X-User-Id`。业务代码的改动集中在中间件一处，不在每个控制器。

**结论三　信封以 `code` 为准，`ret` 保留为兼容字段。** 考试平台只认 `code === "OK"`。若本平台继续只返回 `ret`，对端会把成功当失败。反之本平台读考试平台响应时也必须读 `code`，不能只看 HTTP 200（6.4）。

**结论四　准入必须回源，超时不等于不合格。** 回源超时时返回 `pending`，不是 `prerequisite_missing`。把网络问题判成"你没通过考试"，用户会被无理由挡在项目外，且投诉时无法解释（8.3）。

**结论五　网关不改写业务路径。** 路径版本化在本平台内完成（新增 `/api/v1/workshop` 前缀，旧路径保留一个版本）。网关只做前缀归属与转发，保证 OpenAPI 与实现一致（5.2）。

**结论六　事件本期只能定义，不能生产。** 本平台没有发件箱与投递器，`event-envelope.yaml` 只是契约。任何"等事件到了再放行"的设计在本期都会挂住（8.4）。

### 2.2 身份现状：协议骨架在，链路是自建的

现有实现（`UsersController::login`）能完成"校验密码 → 签发凭证 → 后续请求带凭证"的闭环，但三处与目标形态冲突：

**凭证是自证的。** `token = base64(userid#$email#$encrypt#$ts#$rnd)`，服务端不验签，只解析前 4 段并比对数据库里的 `encrypt`。这意味着：只要拿到 token，30 天内（`system.loginValid` 默认 720 小时）无需任何其他条件即可冒充。没有 revoke 接口，改密码才会更换 `encrypt` 使旧 token 失效。

**第 5 段随机串不参与校验。** 生成时写入了 `$rnd`，校验时 `authFind` 只取前 4 段。这一段的唯一作用是让同一用户多次登录得到不同字符串，避免前端缓存串号——不是安全机制。

**没有 `sub` 概念。** `pre_users` 表没有 `subject` / `openid` / `unionid` 字段，`userid` 是 `bigIncrements`。接入身份中心后必须新增绑定表，不能靠邮箱兜底（邮箱可改、可重复、大小写敏感）。

## 3 目标架构

### 3.1 逻辑架构

```text
浏览器（Vue 2 SPA）
   │  ① HTTPS + 仅会话 Cookie（不出现任何令牌）
   ▼
统一 API 网关  api.jingyuan.edu.cn
   │  ② 校验论坛令牌 / 会话 → 剥离伪造头 → 注入可信头 → 生成 requestId → 限流
   ▼
实训平台  php-fpm 127.0.0.1:8000（Laravel 8）
   ├─ /api/v1/workshop/auth/*     登录、回调、userinfo、登出
   ├─ /api/v1/workshop/*          业务接口：项目、任务、招募、文件（REST 别名）
   ├─ /api/{module}/{method}      旧 RPC 路径（保留一个版本）
```

## 4 统一身份认证流程

### 4.1 身份模型与 `sub` 映射

这是本次对接最关键的一节。两侧的身份主键不同构，必须先建立映射再谈其他。

#### 4.1.1 两侧主键的形态差异

| 项         | 论坛身份中心                      | 实训平台                   | 考试平台            |
| ---------- | --------------------------------- | -------------------------- | ------------------- |
| 字段名     | `sub`（`userinfo.userId`）        | `userid`                   | `userId`（= `sub`） |
| 类型       | 不透明字符串，如 `usr_01J8ZQ7M2K` | `bigint` 自增，如 `10231`  | 字符串              |
| 生成方     | 身份中心，不可变                  | 数据库自增，不可跨环境复用 | 透传 `sub`          |
| 是否可加工 | 不得                              | 无（本地主键）             | 不得                |
| 对外暴露   | 是                                | 否（对端只认 `sub`）       | 是                  |

**结论：不能用 `userid` 冒充 `sub`。** 一旦这么做，考试平台按 `usr_01J8ZQ7M2K` 查不到任何人，事件里的 `data.userId` 也会与对不上号，准入全链路失效。

#### 4.1.2 绑定表

新增一张表，承载 `sub` → `userid` 的映射，不修改 `pre_users` 主键类型。

```sql
CREATE TABLE `pre_user_identity_binding` (
  `id`            BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
  `issuer`        VARCHAR(128) NOT NULL COMMENT '签发方，防多 IdP 串号',
  `subject`       VARCHAR(64)  NOT NULL COMMENT '论坛 sub 原值，不得加工',
  `userid`        BIGINT UNSIGNED NOT NULL COMMENT '本地用户主键',
  `status`        TINYINT      NOT NULL DEFAULT 1 COMMENT '1 生效 0 停用',
  `bound_at`      DATETIME     NOT NULL,
  `last_login_at` DATETIME     NOT NULL,
  PRIMARY KEY (`id`),
  UNIQUE KEY `uk_issuer_subject` (`issuer`, `subject`),
  UNIQUE KEY `uk_userid` (`userid`),
  KEY `idx_bound` (`bound_at`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='统一身份绑定';
```

设计说明：

| 设计点                   | 理由                                                                     |
| ------------------------ | ------------------------------------------------------------------------ |
| `(issuer, subject)` 唯一 | 未来的第二个 IdP（如省平台）不会与论坛的 `sub` 撞号                      |
| `userid` 唯一            | 一个本地账号只绑一个身份，防止一人多号导致项目成员重复                   |
| `subject` 长度 64        | ULID 20 位 + 前缀 4 位，留足余量；不改 `VARCHAR(255)` 是因为唯一索引长度 |
| `status`                 | 解绑不删行，保留审计痕迹                                                 |
| 不存邮箱/手机号          | 身份中心是权威源，本地留副本会过期                                       |

**`subject` 必须原样存储。** 不得 `trim()`、不得转小写、不得截断。论坛若返回带前缀的 `usr_01J8ZQ7M2K`，前缀就是值的一部分。自学平台存的是同一个值，任何一侧加工都会导致跨平台查不到人（对应考试平台文档 8.4 的"最大对接风险"）。

#### 4.1.3 首登建号与并发

用户首次登录时本地不存在映射，需建号。**不要写"先查后插"**——用户连点两次登录，两个请求同时判断"不存在"并各自插入，`uk_issuer_subject` 会报重复键，其中一个请求 500。

正确做法：

```php
try {
    $binding = UserIdentityBinding::create([...]);
} catch (\Illuminate\Database\QueryException $e) {
    // 唯一索引冲突：说明并发建号，改为查询
    if ($this->isDuplicateKey($e)) {
        $binding = UserIdentityBinding::whereIssuer($issuer)->whereSubject($subject)->first();
    } else {
        throw $e;
    }
}
```

建号规则：

| 场景                      | 行为                                                     |
| ------------------------- | -------------------------------------------------------- |
| `sub` 已绑定且 `status=1` | 直接登录，更新 `last_login_at`                           |
| `sub` 已绑定但 `status=0` | 拒绝，返回 `FORBIDDEN`，提示"账号已停用"                 |
| `sub` 未绑定，邮箱已存在  | **不自动关联**。返回 `CONFLICT`，由管理员人工核对后绑定  |
| `sub` 未绑定，邮箱不存在  | 建 `pre_users` 记录 + 绑定，写 `identity=''`（普通用户） |

"邮箱已存在不自动关联"是刻意的：身份中心与本地账号的邮箱可能被不同人持有，自动合并等于把两个账号的数据串在一起。

#### 4.1.4 与考试平台的一致性校验

联调第一天必须做的事：同一个账号在两个平台各查一次 `userinfo`，逐字符比对。

```bash
# 本平台（改造后）
curl -s -b cookie.txt https://api.jingyuan.edu.cn/api/v1/workshop/auth/userinfo | jq -r '.data.userId'
# 考试平台
curl -s -b exam-cookie.txt https://api.jingyuan.edu.cn/api/v1/exam/auth/userinfo | jq -r '.data.userId'
# 两者必须完全相同，包括大小写
```

不一致的三种典型原因，按排查顺序：

1. 本平台仍返回 `userid`（数字）→ 绑定表未生效，`userinfo` 还没改造；
2. 一侧做了 `strtolower()` 或 `prefix` 拼接 → 找到加工点，删掉；
3. 一侧用邮箱兜底生成了 ID → 该账号绑错了，按 `studentNo` 人工核对修正。

### 4.2 当前凭证机制（实测）

目标形态上线前，本节描述的行为是现网实际行为，接入方若现在就要调通，按本节做。

#### 4.2.1 结构

```text
token = base64( userid # $email # $encrypt # $ts # $rnd )
         └──┬──┘   └──┬──┘   └───┬───┘   └┬┘  └┬┘
          主键      邮箱      密码摘要   时间  随机串
```

五段以 `#` 分隔，整体 base64 编码。示例（已脱敏）：

```text
MTAyMzEjI3RlYUBleGFtcGxlLmNvbSMjYWJjMTIzZGVmNDU2IyMxNzYyMjM2MDAwIyN4OXk4ejc=
```

#### 4.2.2 校验过程

| 步  | 动作                                         |
| --- | -------------------------------------------- |
| 1   | 从请求头 `token` 取原始串                    |
| 2   | base64 解码，按 `#` 切分                     |
| 3   | 取第 1 段为主键，查 `pre_users`              |
| 4   | 比对第 3 段与库中 `encrypt`；不一致即失效    |
| 5   | 校验 `identity` 不含 `disable`；含则视为停用 |
| 6   | 通过则注入当前用户                           |

**第 5 段随机串不参与校验。** 它只保证同一用户多次登录得到不同字符串，避免前端缓存串号，不是安全机制。因此"换一个随机串重新登录"不会导致旧凭证失效——旧凭证依然有效。

#### 4.2.3 已知缺陷

| 缺陷               | 影响                                       | 补偿措施                              |
| ------------------ | ------------------------------------------ | ------------------------------------- |
| 无签名，可伪造     | 知道 `userid` 与 `encrypt` 即可构造凭证    | 依赖 `encrypt` 不泄露；网关侧限制来源 |
| 无吊销接口         | 退出登录只删前端存储，服务端凭证仍有效     | 改密码换 `encrypt` 可使全部旧凭证失效 |
| 有效期过长         | `system.loginValid` 默认 720 小时（30 天） | 缩短为 8 小时（见 13.1）              |
| 凭证可被浏览器读取 | 存 localStorage，XSS 即失守                | 目标形态改 HttpOnly Cookie（4.5）     |

**这一节的存在不是为了让人继续用旧机制，而是为了让接入方在改造期间有据可依。** 目标形态上线后，本节整体标记为"历史"。

### 4.3 目标形态：OAuth 2.0 授权码

#### 4.3.1 客户端注册参数

| 参数           | 取值                                                                                           | 说明                                              |
| -------------- | ---------------------------------------------------------------------------------------------- | ------------------------------------------------- |
| `client_id`    | `jy-workshop-web`                                                                              | 每个环境独立注册，不得跨环境复用                  |
| 客户端类型     | 机密客户端（Confidential）                                                                     | 有服务端，必须用 `client_secret`，只存服务端      |
| `redirect_uri` | `https://workshop.jingyuan.edu.cn/api/v1/workshop/auth/oauth/callback`                         | 精确匹配，逐字符核对；测试环境单独注册            |
| 登出回调       | `https://workshop.jingyuan.edu.cn/api/v1/workshop/auth/logged-out`                             | `post_logout_redirect_uri`                        |
| `scope`        | `openid profile`                                                                               | 最小必要；`studentNo` 待身份中心以独立 scope 提供 |
| 授权模式       | `authorization_code`（建议同时启用 PKCE S256）                                                 | 禁止 Implicit 与 Password                         |
| 令牌有效期     | `access_token` 7200 秒，`refresh_token` 按身份中心策略                                         | 是否签发 refresh 由身份中心开关控制，不得假定     |
| 必需端点       | `/oauth/authorize`、`/oauth/token`、`/oauth/userinfo`、`/oauth/introspect`、`/protocol/logout` | 启动时读 Discovery 校验 `issuer`，禁止硬编码      |

**`redirect_uri` 不能指向前端路由。** 若回跳落到 SPA 页面，`code` 会出现在地址栏与浏览器历史里，页面被 XSS 注入时可在换码前劫持。必须指向服务端接口。

#### 4.3.2 令牌只存在于服务端

```text
sess:{sid}                  -> {userid, subject, roles[], accessCipher, refreshCipher, exp}
auth:tk:{sha256}            -> 1                          # 自省结果缓存，TTL 60s
auth:idem:{user}:{key}      -> {status, bodyHash}         # 幂等结果，TTL 24h
auth:csrf:{sid}             -> token                      # CSRF 双提交令牌
auth:state:{state}          -> {redirect, exp}            # 授权 state，TTL 10min
admission:{subject}:{courseId} -> {eligible, reason, exp} # 准入缓存，TTL 60s
```

浏览器侧只能看到 `__Host-workshop_sid`。前端不得读取、拼接或缓存任何令牌。页面刷新后身份由 `GET /api/v1/workshop/auth/userinfo` 恢复。

**这不是"改名"能解决的事。** 现有前端请求拦截器里的 `getToken()` / `setTokens()` 是全局逻辑，改造要连带处理：请求不再注入 `token` 头、401 不再读 localStorage 重试、登出不再只清本地。

### 4.4 登录时序

#### 4.4.1 现状（可直接复现）

| 步  | 参与方 | 动作                                     | 位置                     |
| --- | ------ | ---------------------------------------- | ------------------------ |
| 1   | 浏览器 | 提交邮箱 + 密码到 `/api/users/login`     | 登录页                   |
| 2   | 应用   | 校验密码 → 生成 `encrypt` → 签发 `token` | `UsersController::login` |
| 3   | 浏览器 | 存 localStorage，后续请求带 `token` 头   | 前端拦截器               |
| 4   | 应用   | 每次请求解析 `token` 并查库              | `User::auth()`           |

#### 4.4.2 目标形态（OAuth 授权码 + 服务端换码）

| 步  | 参与方   | 动作                                                                                                                                                       | 本平台实现位置                |
| --- | -------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------- |
| 1   | 浏览器   | 访问受保护页面，未登录时跳 `/api/v1/workshop/auth/login?redirect=/project`                                                                                 | 前端路由守卫                  |
| 2   | 应用     | 生成 `state`（32 字节随机）与 `code_verifier`，`state` 绑会话，10 分钟过期                                                                                 | 新增                          |
| 3   | 应用     | 302 到 `/oauth/authorize?response_type=code&client_id=...&redirect_uri=...&scope=openid%20profile&state=...&code_challenge=...&code_challenge_method=S256` | 新增                          |
| 4   | 身份中心 | 校验 `client_id`、`redirect_uri`、`scope`；未登录则展示登录页                                                                                              | —                             |
| 5   | 用户     | 完成登录并确认授权                                                                                                                                         | —                             |
| 6   | 身份中心 | 302 回 `redirect_uri?code=...&state=...`（`code` 300 秒有效，一次性）                                                                                      | —                             |
| 7   | 应用     | 校验 `state`；不一致则中止、清会话、记安全事件                                                                                                             | 回调首段逻辑                  |
| 8   | 应用     | `POST /oauth/token`（服务端，带 `client_secret` 与 `code_verifier`，超时 3 秒，**禁止重试**）                                                              | 新增                          |
| 9   | 应用     | `GET /oauth/userinfo`，校验 `userId` 非空、与授权阶段一致，取 `roles`                                                                                      | 新增                          |
| 10  | 应用     | 按 `subject` 绑定本地用户（首登建号），建服务端会话，`Set-Cookie`，302 回第 1 步路径                                                                       | 新增会话层                    |
| 11  | 应用     | 写审计日志：时间、`client_id`、`sub`、IP、UA、`state` 校验结果、`requestId`                                                                                | `pre_project_logs` 外的独立表 |

**第 8 步不能重试。** `code` 一次性，超时重试必然拿到 `invalid_grant`，而第一次请求可能已在身份中心侧成功并吊销了 `code`。超时即失败，让用户重走授权。这条与业务接口的重试策略相反，容易写错（9.3）。

**第 9 步失败不得降级放行。** `userinfo` 返回 200 但 `userId` 为空，说明账号体系异常。此时生成临时 ID 让人进去，会产生一批无法与论坛对账的脏数据。

### 4.5 会话规范

| 项           | 要求                                         | 说明                                                |
| ------------ | -------------------------------------------- | --------------------------------------------------- |
| Cookie 名称  | `__Host-workshop_sid`                        | `__Host-` 前缀强制 `Secure`、`Path=/`、无 `Domain`  |
| 属性         | `HttpOnly; Secure; SameSite=Lax; Path=/`     | `Lax` 保证 OAuth 回跳（顶层 GET 导航）能带上 Cookie |
| 有效期       | 空闲 30 分钟，绝对 8 小时                    | 滑动刷新；绝对上限写死配置，不可由前端延长          |
| 服务端存储   | Redis `sess:{sid}`                           | 多实例共享；令牌字段对称加密后落库                  |
| CSRF         | 非 GET 请求校验 `X-CSRF-Token` 双提交        | 与会话绑定，`SameSite=Lax` 不作为唯一防线           |
| 会话固定防护 | 登录成功即重新生成 `sid`                     | 旧 `sid` 立即删除                                   |
| 退出         | 删会话 → 调身份中心 `/protocol/logout` → 302 | 本地失效与远端登出都要做，顺序不可颠倒              |

**页面会话与接口凭证是两套东西，不要混。** 浏览器走会话 Cookie；服务间调用走 L2 签名。目标形态下不存在"浏览器拿 Bearer 调接口"这条路径——那是考试平台文档 Q1 里被否掉的口径。

### 4.6 有效期、续期与吊销

| 场景                   | 行为                                                     | 依据         |
| ---------------------- | -------------------------------------------------------- | ------------ |
| 会话将过期             | 空闲 TTL 滑动刷新；会话内令牌剩余 < 300 秒时在服务端续期 | 会话层       |
| 身份中心未签发 refresh | 回退为静默重授权（`prompt=none`），失败再展示登录页      | 需求文档 8.3 |
| 续期失败               | 清会话 → 跳登录；XHR 场景返回 `AUTH_REQUIRED`            | —            |
| 用户主动退出           | 删会话 → 调 `/protocol/logout` → 302 到 `logged-out`     | 需求文档 8.5 |
| 账号被停用             | 下次自省 `active=false` 立即清会话，返回 `FORBIDDEN`     | 规范 5.4     |

**不得宣称"立即全站退出"。** 身份中心未提供全局会话撤销广播前，最长失效时间等于会话空闲 TTL（30 分钟）。这条限制必须写进验收说明并告知验收方。

### 4.7 环境与开关矩阵

| 环境      | `SSO_MODE`        | 身份来源                       | 适用                         |
| --------- | ----------------- | ------------------------------ | ---------------------------- |
| 本地开发  | `mock`            | 内置 Mock 认证中心（可选身份） | 单人自测、离线复现，界面标注 |
| 联调/测试 | `real` + 测试租户 | 论坛测试账号（三类角色各一）   | 跨平台联调、验收             |
| 生产      | `real`            | 论坛身份中心                   | 正式运行                     |

**Mock 只用于打通链路，不用于验收。** Mock 不校验 `redirect_uri` 精确匹配、不模拟令牌吊销、不校验 PKCE。这三项恰是真实环境最容易出错的地方，必须在阶段五用真实身份中心重跑。

## 5 网关接入方式

本章是任务书。每一条都能直接转成配置项或代码。

### 5.1 分工边界

| 事项                 | 网关      | 实训平台                | 说明                                     |
| -------------------- | --------- | ----------------------- | ---------------------------------------- |
| TLS 终止             | ✓         | —                       | 上游走私网 HTTP                          |
| 令牌校验             | ✓         | —                       | 网关调自省，本平台不解析令牌             |
| 可信头注入           | ✓         | —                       | 见 5.3                                   |
| 伪造头剥离           | ✓         | —                       | 入站同名头必须先删                       |
| 内部签名校验         | —         | ✓                       | 网关注入，本平台验签（5.5）              |
| 限流                 | ✓         | —                       | 见 5.6                                   |
| 权限点与数据归属     | —         | ✓                       | 网关切不动业务规则                       |
| requestId 生成与回带 | ✓（生成） | ✓（回带响应体与响应头） | 网关生成的 `X-Request-Id` 本平台必须沿用 |

**网关不得做的事：**

| #   | 禁止                           | 原因                                   |
| --- | ------------------------------ | -------------------------------------- |
| 1   | 改写业务路径                   | 会让 OpenAPI 与实现版本错位            |
| 2   | 判断"这个学生能不能进这个项目" | 业务规则，网关无权                     |
| 3   | 缓存业务响应                   | 成员变更、报名状态是实时的             |
| 4   | 把 `X-App-Code` 当作认证       | 客户端可伪造                           |
| 5   | 对 POST 无条件重试             | 报名、加成员非幂等，重试会产生重复数据 |

### 5.2 路由规划与上游映射

| 网关对外路径                           | 上游（本平台）       | 鉴权           | 说明                       |
| -------------------------------------- | -------------------- | -------------- | -------------------------- |
| `/api/v1/workshop/*`                   | `/api/v1/workshop/*` | L1 会话校验    | 业务接口主体（新前缀）     |
| `/api/v1/workshop/auth/login`          | 同路径               | 无（白名单）   | 发起授权                   |
| `/api/v1/workshop/auth/oauth/callback` | 同路径               | 无（靠 state） | 授权回跳，必须在白名单     |
| `/api/v1/workshop/auth/userinfo`       | 同路径               | L1             | 身份恢复                   |
| `/api/v1/workshop/auth/logout`         | 同路径               | L1             | 退出                       |
| `/api/v1/workshop/internal/*`          | 同路径               | L2 签名        | 服务间调用，不对浏览器开放 |
| `/api/v1/workshop/health`              | 同路径               | 无（白名单）   | 健康检查                   |
| `/api/{module}/{method}`（旧 RPC）     | 同路径               | L1             | 保留一个版本，见 6.1       |

**`/api/v1/workshop/*` 是精确前缀，不能写成 `/api/*`。** 写成 `/api/*` 会把考试平台的 `/api/v1/exam/*`、自学平台的 `/api/v1/learning/*` 一起吃进来，两个平台路由互相覆盖，排查时的现象是"项目接口返回了考试成绩"。

**旧路径的处理。** 现有前端有 300 多处调用拼在 `/api/{module}/{method}` 上。做法是应用内增加一个前缀常量与一条兼容路由（`/api/v1/workshop/*` → 内部重写回 RPC 派发），前端只改一处 base URL，逐步替换。网关侧同时保留两条路由，一个版本后下线旧的。

### 5.3 请求头规范

#### 5.3.1 客户端入站头

| 头名              | 方向                 | 必填       | 规则                                                       |
| ----------------- | -------------------- | ---------- | ---------------------------------------------------------- |
| `X-Request-Id`    | 客户端 → 网关 → 服务 | 否         | 缺省由网关生成 UUID v4；服务端必须在响应体与响应头回带同值 |
| `X-App-Code`      | 客户端 → 网关        | 是         | 调用本平台填 `workshop`；跨平台调用填发起方编码            |
| `Idempotency-Key` | 客户端 → 网关        | 写操作必填 | 报名、加成员、审批、发准入类接口必须携带                   |
| `Cookie`          | 浏览器 → 网关 → 服务 | 是         | 仅 `__Host-workshop_sid`；不透传其他 Cookie                |
| `Content-Type`    | 客户端 → 网关 → 服务 | 写必填     | 必须是 `application/json`，见 6.3                          |

#### 5.3.2 网关注入的可信头

| 头名              | 示例               | 本平台处理方式                                                  |
| ----------------- | ------------------ | --------------------------------------------------------------- |
| `X-User-Id`       | `usr_01J8ZQ7M2K`   | 作为 `subject`；为空表示匿名，仅公开只读接口可放行              |
| `X-User-Role`     | `student`          | 解析为角色数组，映射到权限点（7.2）；不得直接写 `identity` 字段 |
| `X-Client-Id`     | `jy-workshop-web`  | 记入审计日志，区分 Web 与小程序来源                             |
| `X-Token-Exp`     | `1762243200`       | 秒级时间戳；长任务据此判断是否需提前续期                        |
| `X-Request-Id`    | `7f3c9a2e-...`     | 写入日志与响应体 `requestId`，全链路追踪                        |
| `X-Auth-Mode`     | `user` / `service` | 决定走用户态还是服务态；`service` 模式下不得写用户私有数据      |
| `X-Timestamp`     | `1762236000`       | 参与内部签名，缺失即视为非法请求                                |
| `X-Internal-Sign` | `hmac(...)`        | 对上述字段按固定顺序计算的 HMAC-SHA256，必须校验                |

**`X-User-Role` 只放统一角色。** `moderator`、`banned` 这类平台特有角色不跨平台传递。网关注入前完成映射，业务侧不再做二次翻译。

#### 5.3.3 本平台响应头

| 头名            | 值                                | 说明                  |
| --------------- | --------------------------------- | --------------------- |
| `X-Request-Id`  | 与响应体 `requestId` 相同         | 必须回带，便于对账    |
| `Content-Type`  | `application/json; charset=utf-8` | 与 6.3 的判定条件对应 |
| `Cache-Control` | `no-store`                        | 业务接口不缓存        |

### 5.4 公开路径白名单

下列路径不挂令牌校验，否则登录本身会被 401 挡住，形成死锁。

| 路径                                   | 原因                           | 网关动作                         |
| -------------------------------------- | ------------------------------ | -------------------------------- |
| `/api/v1/workshop/auth/login`          | 发起授权，此时还没有令牌       | 放行并限流（10 次/分钟/IP）      |
| `/api/v1/workshop/auth/oauth/callback` | 回跳带 `code`，靠 `state` 防伪 | 放行，剥离入站 `X-User-*`        |
| `/api/v1/workshop/auth/logout`         | 登出，会话可能已失效           | 放行，仍注入可信头（若有）       |
| `/api/v1/workshop/health`              | 探活                           | 放行，只允许 GET                 |
| `/oauth/*`（身份中心）                 | 授权与换令牌                   | 放行，拒绝 `response_type=token` |

**白名单必须是精确路径，不能用前缀通配。** 写成 `/api/v1/workshop/auth/*` 就包括了 `/auth/userinfo`，等于把身份接口暴露给未登录请求。逐条列，纳入代码评审。

### 5.5 可信头防伪造

"边缘清除外部同名头"是必要条件，不是充分条件。若上游端口能被内网直接访问，攻击者绕过网关直接发 `X-User-Id` 就能冒充任何人。因此本平台**必须**校验 `X-Internal-Sign`。

#### 5.5.1 规范化串

```text
canonical = X-User-Id \n X-User-Role \n X-Client-Id \n X-Token-Exp \n
            X-Request-Id \n X-Auth-Mode \n X-Timestamp

X-Internal-Sign = hex( HMAC-SHA256( internalSignSecret, canonical ) )
```

字段缺失以空串占位，顺序固定不可调整。任何一侧改了顺序，验签必然失败。

#### 5.5.2 校验结果与处置

| 校验结果             | 处置                                      | 说明                                |
| -------------------- | ----------------------------------------- | ----------------------------------- |
| 签名缺失             | 403 `FORBIDDEN`，审计标记 `direct_access` | 视为绕过网关直连，需告警            |
| 签名不一致           | 403，记录期望值与收到值的**摘要**         | 不同时记录明文，防日志泄露密钥材料  |
| 时间戳超窗（> 300s） | 403，记录偏移秒数                         | 强制 NTP；偏移 > 30s 告警           |
| 来源不在网关网段     | 403                                       | 与签名双重判断，缺一不可            |
| 校验通过             | 信任 `X-User-Id` 与 `X-User-Role`         | 仍须执行权限点与数据归属校验（7.3） |

#### 5.5.3 开发开关

本地直连调试时可设 `GATEWAY_VERIFY_SIGN=false` 跳过验签，但：

- 启动时打印醒目告警（`storage/logs` 与 stdout 各一行）；
- 测试环境启动脚本显式置 `true`；
- 生产环境缺该变量时**默认开启**验签，不是默认关闭。

靠配置评审卡住，不靠人记得。

### 5.6 限流、超时与体积

| 项                | 建议值                                  | 对本平台的影响                                 |
| ----------------- | --------------------------------------- | ---------------------------------------------- |
| 单用户限流        | 20 QPS（令牌桶）                        | 项目看板首屏建议 ≤ 3 个请求                    |
| 单 IP 限流        | 60 QPS                                  | 机房出口 NAT 场景可能误伤，按 `X-User-Id` 优先 |
| 登录端点限流      | 10 次/分钟/IP                           | 防授权码枚举                                   |
| 网关 → 上游总超时 | 30 s（默认），导出类 120 s              | 项目导出、日志导出单独放宽                     |
| 网关 → 身份中心   | 自省 800 ms；换令牌 3 s                 | 换令牌不可重试                                 |
| 网关 → 考试平台   | 准入查询 2 s（本平台侧再设 1.5 s 更短） | 见 8.3；超时返回 `pending` 而非拒绝            |
| 请求体上限        | 2 MB；文件上传单独放行 50 MB            | 超限 413                                       |
| 响应体上限        | 8 MB                                    | 大文件走流式                                   |

**准入查询的超时要短于网关总超时。** 若两侧都设 2 秒，网关先超时返回 504，本平台还没来得及写 `pending` 结论，用户看到的是网关错误页而不是"资格校验中"。本平台侧设 1.5 秒，留 500ms 给自己写响应。

### 6.3 请求约定

| 项       | 要求                                                                                     |
| -------- | ---------------------------------------------------------------------------------------- |
| 方法     | 读用 GET，写用 POST；不做 PUT/PATCH/DELETE 的语义拆分（存量接口保持 POST）               |
| 编码     | 请求体 `application/json`；文件上传 `multipart/form-data`                                |
| 字段命名 | 对外一律 `snake_case`（存量前端依赖），新增 `/v1` 接口用 `camelCase`，同一接口内不得混用 |
| 时间     | RFC 3339 带时区，如 `2026-11-05T09:12:33+08:00`；禁止无时区字符串                        |
| ID       | 对外字符串；`userid` 不直接暴露给跨平台调用方，用 `subject`                              |
| 空值     | 缺失字段不返回；可空字段显式 `null`；**不得**用空串代替 `null`                           |
| 排序     | `sort=field:asc`，字段白名单校验，拒绝任意列名                                           |

**`Content-Type` 是硬条件。** 写接口不带 `Content-Type: application/json` 时，框架会把请求当成表单处理，异常路径会返回 HTML 错误页而不是 JSON。判定条件是 `Content-Type` **严格等于** `application/json`——带 `; charset=utf-8` 就不匹配。读接口也建议带上，症状一致但更难排查。

### 6.4 统一响应信封与互操作

#### 6.4.1 本平台信封（现状 + 叠加）

```json
{
  "ret": 1,
  "msg": "success",
  "data": { "items": [] },
  "code": "OK",
  "requestId": "req_7f3c9a2e5b1d4c80a9f2"
}
```

| 字段        | 类型   | 语义                                               |
| ----------- | ------ | -------------------------------------------------- |
| `ret`       | int    | `> 0` 成功，`<= 0` 失败；存量前端唯一判据          |
| `msg`       | string | 人类可读消息，可能是中文业务提示                   |
| `data`      | any    | 业务数据；**失败时不是 `null`**，而是 `{}` 或 `[]` |
| `code`      | string | 跨平台规范码，9 个取值，见 6.5                     |
| `requestId` | string | 追踪号，与响应头 `X-Request-Id` 相同               |

`code` 与 `requestId` 由 `PlatformContract` 中间件在响应体末尾追加，只在「JSON 对象且含 `ret` 键」时生效。文件流、HTML、非 JSON 响应不叠加。

#### 6.4.2 考试平台信封

```json
{ "code": "OK", "message": "success", "data": {}, "requestId": "..." }
```

**没有 `ret`，没有 `msg`。** 成功判定只看 `code === "OK"`。

#### 6.4.3 双向互操作规则

这是本节的要害。两侧信封不同构，必须有一套明确的转换规则，否则联调时会出现"双方都以为自己是对的"。

**规则一：对外一律以 `code` 为成功判据。**

| 场景                 | 错误做法                 | 正确做法                                   |
| -------------------- | ------------------------ | ------------------------------------------ |
| 考试平台读本平台响应 | 找 `ret`，找不到就判失败 | 读 `code`；`ret` 只作日志辅助              |
| 本平台读考试平台响应 | 看 HTTP 200 就当成功     | 读 `code`；HTTP 200 + `FORBIDDEN` 是可能的 |
| 本平台内部存量前端   | 改判 `code`              | 保持读 `ret`，本期不动                     |

**规则二：本平台对外提供 `message` 别名（△ 待实施）。** 考试平台的通用客户端会读 `message`。当前本平台只返回 `msg`，对端拿到 `undefined`，错误提示会空白。补法是在中间件里追加 `message`（值等于 `msg`），不改 `msg` 本身。

**规则三：`data` 失败时不得为 `null`。** 存量行为是返回 `{}` 或 `[]`。对端如果按"`data === null` 表示失败"来判断会误判——`code` 才是判据。这一点必须在联调前告知对端。

**规则四：`requestId` 必须双向透传。** 本平台调考试平台时，把当前请求的 `requestId` 放进 `X-Request-Id`；考试平台回包里的 `requestId` 记入日志。这样一次用户操作产生的跨平台调用可以用一个 ID 串起来。

映射对照：

| 语义     | 本平台      | 考试平台    | 转换                                 |
| -------- | ----------- | ----------- | ------------------------------------ |
| 成功标志 | `ret > 0`   | `code=OK`   | 以 `code` 为准；`ret` 仅兼容存量前端 |
| 提示文案 | `msg`       | `message`   | 本平台补 `message` 别名              |
| 业务数据 | `data`      | `data`      | 同构                                 |
| 追踪号   | `requestId` | `requestId` | 同构，值必须相同                     |

### 6.5 错误码映射

#### 6.5.1 本平台的 9 个码

| `code`                | HTTP | 触发条件                               | 典型 `msg`         |
| --------------------- | ---- | -------------------------------------- | ------------------ |
| `OK`                  | 200  | `ret > 0`                              | `success`          |
| `VALIDATION_ERROR`    | 400  | 参数缺失/非法、`X-App-Code` 不在白名单 | `APP_CODE_INVALID` |
| `AUTH_REQUIRED`       | 200  | 未登录（`ret=-1`）、部分业务拒绝       | `请登录后继续...`  |
| `FORBIDDEN`           | 403  | 无权限                                 | `无权访问`         |
| `NOT_FOUND`           | 200  | 对象不存在、方法不存在                 | `404 not found`    |
| `CONFLICT`            | 409  | 状态冲突                               | `当前招募不可报名` |
| `BUSINESS_ERROR`      | 200  | 业务规则拒绝                           | `你已在队伍中`     |
| `SERVICE_UNAVAILABLE` | 503  | 依赖不可用                             | `服务暂不可用`     |
| `INTERNAL_ERROR`      | 500  | 未预期异常                             | `服务器内部错误`   |

**`AUTH_TOKEN_EXPIRED` 永远不会出现。** `openapi.yaml` 的枚举列了它，但中间件没有产出点。接入方不要为这个码写专门分支——本平台无法区分"未登录"与"过期"，两者都是 `AUTH_REQUIRED`。这是已知缺口（G06），修法是补产出点或从枚举删除，本期未定。

#### 6.5.2 与考试平台的码对照

| 本平台 `code`         | 考试平台 `code`       | 考试平台数字码        | 转换规则                                          |
| --------------------- | --------------------- | --------------------- | ------------------------------------------------- |
| `OK`                  | `OK`                  | 0                     | 直通                                              |
| `VALIDATION_ERROR`    | `VALIDATION_ERROR`    | 40001 / 40002         | 直通；`reason` 放 `data.reason`                   |
| `AUTH_REQUIRED`       | `AUTH_REQUIRED`       | 40101 / 40102         | 直通                                              |
| `AUTH_REQUIRED`       | `AUTH_TOKEN_EXPIRED`  | 40103 / 40104         | **本平台无法产出**，收到时按 `AUTH_REQUIRED` 处理 |
| `FORBIDDEN`           | `FORBIDDEN`           | 40301 / 40302 / 40303 | 直通；`40303` 表示绕过网关，需告警                |
| `NOT_FOUND`           | `NOT_FOUND`           | 40401                 | 直通                                              |
| `CONFLICT`            | `CONFLICT`            | 40901                 | 直通                                              |
| `BUSINESS_ERROR`      | `BUSINESS_ERROR`      | —                     | 直通                                              |
| `VALIDATION_ERROR`    | `PAYLOAD_TOO_LARGE`   | —                     | 本平台无独立码，超限返回 `VALIDATION_ERROR`       |
| `SERVICE_UNAVAILABLE` | `SERVICE_UNAVAILABLE` | 50301                 | 直通；回源超时时本平台返回此码                    |
| `INTERNAL_ERROR`      | `INTERNAL_ERROR`      | —                     | 直通                                              |

**`40300` 是网关保留码**（路由未配鉴权策略），业务侧不得占用。出现即告警。

**HTTP 状态码与 `code` 必须成对出现。** 不得出现 `200 + FORBIDDEN`。现状本平台未登录返回 `200 + ret=-1 + AUTH_REQUIRED`，这是历史行为（DV-04），改造时统一为 401。

| `GET /api/recruitment/lists`  | `page`、`pagesize`            |       50        | 100  | 同上                                         |
| `GET /api/users/search`       | `keyword`、`page`、`pagesize` |       10        | 100  | 同上                                         |
| `GET /api/file/lists`         | 无分页                        |        —        | 500  | 一次返回全部（受 500 条上限约束）            |

**默认值不一致是历史遗留，不是约定。** 接入方必须显式传 `pagesize`，不要依赖默认值。超上限时本平台行为是**截断到上限**（不报错），这是与考试平台不同的地方——考试平台返回 `VALIDATION_ERROR`。跨平台调用时若依赖严格报错，需自行先校验。

### 6.7 幂等与重试

#### 6.7.1 幂等键

| 项       | 要求                                                                |
| -------- | ------------------------------------------------------------------- |
| 头名     | `Idempotency-Key`                                                   |
| 必填接口 | 报名（`recruitment/apply`）、加成员、审批（`review/apply`）、发准入 |
| 键格式   | 建议 UUID v4，8–128 位                                              |
| 存储     | Redis `auth:idem:{subject}:{method}:{path}:{key}`                   |
| TTL      | 成功 24 小时；处理中 60 秒                                          |
| 作用域   | 必须绑定调用者身份，禁止跨用户复用                                  |
| 缓存内容 | 仅缓存 2xx 结果；业务失败（4xx）不缓存                              |

判定顺序：

```text
1. 取 Idempotency-Key，缺失 → 400 VALIDATION_ERROR
2. 命中且已完成 → 直接返回缓存 {status, body}
3. 命中且处理中 → 409 CONFLICT
4. 未命中 → 写占位（EX 60s）→ 业务事务 → 覆盖为最终结果（EX 24h）
```

**报名是最需要幂等的接口。** 现状靠唯一索引 `uk_pra_recruit_applicant` 兜底，重复提交会返回"你已报名，请勿重复提交"，语义正确但不是幂等。加幂等键后，同一 key 的第二次请求直接返回第一次的结果，前端体验一致。

#### 6.7.2 重试策略

| 场景              | 是否重试 | 说明                        |
| ----------------- | :------: | --------------------------- |
| 读接口 5xx        |    是    | 指数退避，最多 2 次         |
| 读接口超时        |    是    | 同上                        |
| 写接口无幂等键    |  **否**  | 可能产生重复数据            |
| 写接口带幂等键    |    是    | 最多 2 次，间隔 1s / 3s     |
| 401 / 403         |  **否**  | 重试不会改变结论            |
| 400 / 409         |  **否**  | 契约或状态错误              |
| 429               |    是    | 按 `Retry-After` 等待       |
| 换码请求（OAuth） |  **否**  | `code` 一次性，重试必然失败 |

### 6.8 CORS

| 项       | 要求                                                                            |
| -------- | ------------------------------------------------------------------------------- |
| 允许来源 | 显式白名单（`https://workshop.jingyuan.edu.cn` 等），禁用 `*`                   |
| 允许头   | `Content-Type`、`X-Request-Id`、`X-App-Code`、`Idempotency-Key`、`X-CSRF-Token` |
| 暴露头   | `X-Request-Id`                                                                  |
| 允许方法 | `GET, POST, OPTIONS`                                                            |
| 凭证     | `Access-Control-Allow-Credentials: true`（与会话 Cookie 配套）                  |
| 预检缓存 | `Access-Control-Max-Age: 600`                                                   |

**`Access-Control-Allow-Origin` 不能为 `*` 且同时带 Credentials。** 浏览器会直接拒绝。必须回显具体来源。

### 6.9 OpenAPI 交付

| 项       | 要求                                                                                |
| -------- | ----------------------------------------------------------------------------------- |
| 位置     | `docs/platform/openapi.yaml`（OpenAPI 3.0.3），与代码同一提交                       |
| 覆盖     | 表 6-1 的 23 个接口 + 表 6-2 新增接口                                               |
| 对账     | `npm run typecheck` 校验文档 path 与控制器方法双向一致，改错方法名会失败            |

| 变更规则 | 破坏性变更（删字段、改类型、改枚举）新增 `/v2` 并保留迁移期；新增可选字段属兼容变更 |

## 7 权限与角色

### 7.1 账号类型与状态

| 类型     | 判定                            | 能力                           |
| -------- | ------------------------------- | ------------------------------ |
| 匿名     | 无会话                          | 仅 `system/setting` 等公开只读 |
| 普通用户 | 已登录，`identity` 不含 `admin` | 项目/任务/招募的常规操作       |
| 管理员   | `identity` 含 `admin`           | 跨项目操作、系统配置           |
| 服务账号 | `X-Auth-Mode: service`          | 服务间接口，不得写用户私有数据 |

| 状态   | 判定                      | 表现                                   |
| ------ | ------------------------- | -------------------------------------- |
| 正常   | `identity` 不含 `disable` | 正常                                   |
| 停用   | `identity` 含 `disable`   | 登录被拒；已签发凭证在下一次请求时失效 |
| 需改密 | `changepass = 1`          | 登录后强制跳改密                       |

**停用标记以 `identity` 字段为准**，`disable_at` 只是同步记录，不参与判定。

### 7.2 角色映射

| 规范角色  | 平台对应              | 说明                                           |
| --------- | --------------------- | ---------------------------------------------- |
| `student` | 普通登录用户          | 无显式标记；`identity` 不含 `admin` 即视为学生 |
| `teacher` | **无此角色**          | 平台不区分教师，教师操作与普通成员相同         |
| `admin`   | `identity` 含 `admin` | 系统管理员                                     |

规范要求角色由统一身份中心下发。接入前，上表只是**投影**，不构成权威（DV-01）。**不得**据学号推断角色，也不得在前端隐藏按钮当作授权。

### 7.3 权限判定与数据归属

平台没有 `{resource}:{action}` 授权表，实际授权由三层逻辑组成：

| 判定方式       | 实现位置                                          | 语义                                         |
| -------------- | ------------------------------------------------- | -------------------------------------------- |
| 数据范围作用域 | `Project::authData()` / `ProjectTask::authData()` | 查询自动附加「我是成员」条件，越权对象查不到 |
| 显式归属判断   | 控制器内 owner 校验                               | 高敏操作要求调用者即资源所有者               |
| 管理员标志     | `User::isAdmin()`                                 | 系统级配置与跨项目操作                       |

| 权限点                 | 需登录 | 实际判定位置                     | 状态     |
| ---------------------- | :----: | -------------------------------- | -------- |
| `project:read`         |   是   | `Project::authData()`            | 已实现   |
| `project:create`       |   是   | `ProjectController::add()`       | 已实现   |
| `project:update`       |   是   | 项目归属                         | 已实现   |
| `project:invite`       |   是   | `ProjectController::invite()`    | 已实现   |
| `project:transfer`     |   是   | 仅所有者                         | 已实现   |
| `project:archive`      |   是   | 仅所有者                         | 已实现   |
| `task:read`            |   是   | `ProjectTask::authData()`        | 已实现   |
| `task:create`          |   是   | 项目成员                         | 已实现   |
| `task:update`          |   是   | 成员/负责人                      | 已实现   |
| `recruitment:read`     |   是   | `RecruitmentController::lists()` | 已实现   |
| `recruitment:publish`  |   是   | 仅项目成员                       | 已实现   |
| `recruitment:apply`    |   是   | 登录用户 + 唯一索引              | 已实现   |
| `recruitment:review`   |   是   | 仅发布者                         | 已实现   |
| `recruitment:close`    |   是   | 仅发布者 + 状态机                | 已实现   |
| `admission:read`       |   是   | 待实现（回源 + 缓存）            | △ 待实现 |
| `file:read`            |   是   | 文件所属项目数据范围             | 已实现   |
| `file:upload`          |   是   | 项目成员                         | 已实现   |
| `system:setting:read`  |   否   | `SystemController::setting()`    | 已实现   |
| `system:setting:write` |   是   | `User::isAdmin()`                | 已实现   |

**服务端四重校验**（改造后必须逐条满足）：

1. **身份有效**：会话存在、`X-Internal-Sign` 校验通过、`roles` 非空；
2. **权限点满足**：路由声明的权限点被角色矩阵覆盖，缺一即 403；
3. **数据归属**：项目的所有者、报名的申请人必须与当前 `subject` 比对；
4. **业务状态**：只有 `recruiting` 可报名；已 `full` 的招募不再接受审批通过。

### 7.4 招募与报名状态机

#### 7.4.1 招募状态

```text
recruiting ──满员──► full ──开始──► in_progress ──► completed
     │                  │                              │
     └──────────────────┴──────────► closed ◄──────────┘
```

| 状态          | 含义   | 可执行动作                 |
| ------------- | ------ | -------------------------- |
| `recruiting`  | 招募中 | 报名、审批、关闭、直接加人 |
| `full`        | 已满员 | 开始、关闭；不接受新报名   |
| `in_progress` | 进行中 | 完成、关闭                 |
| `completed`   | 已完成 | 关闭（终态）               |
| `closed`      | 已关闭 | 无（终态）                 |

合法流转由 `RecruitmentController::status()` 校验，非法流转返回 `ret=-1` + `非法状态流转：x -> y`。仅招募发布者可执行。

**状态机是准入校验之后的一道闸。** 报名时先判 `recruiting`，再判准入；两者都过才写记录。顺序不能反——对着一个已关闭的招募去回源考试平台，纯属浪费一次跨平台调用。

#### 7.4.2 报名状态

```text
        ┌──────────── 重复报名（终态复位） ────────────┐
        ▼                                              │
     pending ──通过──► approved ──(入队/满员判定)       │
        │                                              │
        ├──拒绝──► rejected ───────────────────────────┘
        │
        └──撤回──► withdrawn ──────────────────────────┘
```

| 状态        | 含义   | 说明                                       |
| ----------- | ------ | ------------------------------------------ |
| `pending`   | 待审批 | 报名后的初始态；准入未过时不产生该记录     |
| `approved`  | 已通过 | 同时写入 `pre_project_recruitment_members` |
| `rejected`  | 已拒绝 | 可重新报名（复位为 `pending`）             |
| `withdrawn` | 已撤回 | 同上                                       |

`pending` 与 `approved` 状态下重复报名会被拒绝；`rejected` 与 `withdrawn` 允许复位重报。唯一索引 `uk_pra_recruit_applicant` 是最后一道兜底。

准入结论与报名状态是**两条独立的状态线**：准入决定"能不能报"，报名状态决定"报上了没有"。不要把 `eligible=false` 写成 `rejected`——前者根本没产生记录。

### 7.5 越权表现与审计

**本平台不返回 403 的场景：**

| 场景           | 表现                                           | 原因                  |
| -------------- | ---------------------------------------------- | --------------------- |
| 列表接口越权   | 自动过滤，看不到非成员数据                     | `authData()` 数据范围 |
| 单对象接口越权 | 查不到（空结果/错误）                          | 同上                  |
| 归属校验类操作 | `ret=-1` + 中文提示，`code` 为 `AUTH_REQUIRED` | DV-08 语义复用        |

接入方做权限预判时，**只能以"接口是否返回数据"为准**，不要依赖固定的 403。

| 审计能力       | 现状                                                                                   | 位置                               |
| -------------- | -------------------------------------------------------------------------------------- | ---------------------------------- |
| 业务操作留痕   | 项目/任务变更写入 `pre_project_logs`（`project_id`、`userid`、`detail`、`created_at`） | 数据库                             |
| 请求级访问日志 | 每次 `/api/**` 请求一行 JSON，含 `requestId`、`appCode`、方法、路径、状态、耗时、IP    | `storage/logs/platform-access.log` |
| 按追踪号追查   | 支持：响应头/响应体 `requestId` 与访问日志一一对应                                     | 同上                               |
| 审计字段完整性 | `pre_project_logs` **缺** `requestId` 与结果字段                                       | G15，本期补                        |

### 7.6 权限红线

| 编号 | 禁止事项                              | 原因                   |
| ---- | ------------------------------------- | ---------------------- |
| P1   | 在前端以隐藏按钮作为授权手段          | 所有拦截均在服务端     |
| P2   | 据学号推断角色                        | 规范 §5.1 明确禁止     |
| P3   | 新增 `teacher` 角色或自行扩展角色枚举 | 角色权威在统一身份中心 |
| P4   | 在日志中写入凭证、密码、完整请求体    | 泄露即账号失守         |
| P5   | 以 `X-App-Code` 作为来源认证          | 客户端可伪造           |
| P6   | 用 `userid` 代替 `sub` 对外           | 跨平台断链，见 4.1     |

## 8 数据交互规则

本章规定实训平台与考试平台之间"什么数据、以什么形态、在什么时候"流动。凡涉及跨平台取数或落库的，都以本章为准。

### 8.1 交互总览

```text
                  ┌──────────────────────┐
                  │   论坛身份中心       │
                  │   sub / roles        │
                  └──────────┬───────────┘
                             │ ① 登录换码取 userinfo
                             ▼
   ┌───────────────────┐        ② 准入查询（同步，L2 签名）        ┌──────────────────┐
   │   实训平台        │ ───────────────────────────────────────► │   考试平台       │
   │   workshop        │ ◄─────────────────────────────────────── │   exam           │
   │                   │        eligible + reason + score         │                  │
   │  准入投影表       │                                          │  准入权威源      │
   │  （只加速）       │        ③ 事件 exam.passed / failed        │                  │
   └─────────┬─────────┘ ◄─────────────────────────────────────── └──────────────────┘
             │                        （异步，本期△）
             │ ④ 项目参与记录
             ▼
       成长档案（二期）
```

四个方向的数据特征：

| 方向       | 数据量级       | 时效要求         | 一致性要求     | 失败可容忍度   |
| ---------- | -------------- | ---------------- | -------------- | -------------- |
| ① 登录     | 每用户每次登录 | 实时（< 3s）     | 强一致         | 不可容忍       |
| ② 准入查询 | 每报名一次     | 实时（< 1.5s）   | 强一致（权威） | 可降级为"待定" |
| ③ 事件     | 每次考试结束   | 最终一致（分钟） | 幂等           | 可延迟，不可丢 |
| ④ 项目记录 | 每次项目完成   | 最终一致（小时） | 幂等           | 可延迟         |

### 8.2 ID 与字段对齐

#### 8.2.1 字段对照

| 语义     | 实训平台                    | 考试平台                 | 对齐规则                                   |
| -------- | --------------------------- | ------------------------ | ------------------------------------------ |
| 用户主键 | `userid`（bigint）          | `userId`（= `sub`）      | 经绑定表映射，对外只暴露 `subject`         |
| 项目     | `project_id`（bigint）      | —                        | 仅本平台内使用，不外传                     |
| 招募     | `recruitment_id`（bigint）  | —                        | 同上                                       |
| 课程     | `course_id`（字符串，新增） | `courseId`               | 原值存储，本平台不生成课程 ID              |
| 考试     | —                           | `examId`                 | 只透传展示，不落库                         |
| 成绩     | —                           | `score`（整数）          | 只读，不落库，见 8.6                       |
| 平台编码 | `workshop`                  | `exam`                   | 事件 `sourcePlatform` 与 `X-App-Code` 同值 |
| 时间     | RFC 3339 带时区             | 同                       | 统一带时区；事件封套用 UTC                 |
| 规则版本 | —                           | `ruleVersion`（如 `v1`） | 透传存储，供下游复算                       |

#### 8.2.2 三类 ID 的处理纪律

| 类型       | 纪律                                                                 |
| ---------- | -------------------------------------------------------------------- |
| `sub`      | 原值透传，不 trim、不转小写、不截断、不加前缀                        |
| `courseId` | 以考试平台返回的形态为准；本平台只存不改。`course_9` 与 `9` 是两个值 |
| 本地主键   | 不出本平台；跨平台调用一律换成 `subject` 或业务 ID                   |

**禁止"用邮箱生成一个稳定 ID"。** 邮箱可改、可重复、大小写敏感，任何基于它的哈希都会在用户改邮箱后断链。

#### 8.2.3 时间口径

| 场景                  | 格式                | 示例                        |
| --------------------- | ------------------- | --------------------------- |
| 业务时间（给人看）    | RFC 3339 带本地时区 | `2026-11-05T09:12:33+08:00` |
| 事件封套 `occurredAt` | RFC 3339 UTC（`Z`） | `2026-11-05T01:12:33Z`      |
| 数据库存储            | `DATETIME`（UTC）   | `2026-11-05 01:12:33`       |
| 超时/有效期           | 秒（整数）          | `7200`                      |

**封套时间用 UTC，业务时间用 +08:00，两者不得混用。** 混用会导致"事件比业务时间早 8 小时"的排查乌龙——这类问题在联调期平均要花半天。

### 8.3 准入判定：必须回源

这是与考试平台对接的核心逻辑，判定顺序固定，不能颠倒。

#### 8.3.1 判定流程

```text
报名请求（recruitment_id, 可选 course_id）
   │
   ├─ course_id 为空 ──────────────────────────► 跳过准入，直接走原报名流程
   │
   ├─ 查本地投影 pre_exam_admission_projection
   │     ├─ 命中且未过期（≤ 5 分钟）──────────► 用投影结论（快路径）
   │     └─ 未命中或已过期
   │            │
   │            ├─ 调考试平台 GET /admissions/{subject}/{courseId}
   │            │     超时 1.5s
   │            │     ├─ eligible=true  ─────► 放行，刷新投影
   │            │     ├─ eligible=false ─────► 拒绝，reason 原样带给用户
   │            │     └─ 超时 / 5xx ────────► 返回 pending，提示"资格校验中"
   │            │
   │            └─ 回源异常但投影有旧值 ────► 仍返回 pending（不用旧值拒绝）
```

#### 8.3.2 `reason` 枚举与用户提示

| `reason`               | 含义           | 本平台处置   | 用户提示                     |
| ---------------------- | -------------- | ------------ | ---------------------------- |
| `passed`               | 已通过         | 放行         | —                            |
| `not_started`          | 未参加考试     | 拒绝         | 请先完成「课程名」考试       |
| `failed`               | 未通过         | 拒绝         | 考试成绩未达标，请重新考试   |
| `violation`            | 违规超限       | 拒绝         | 考试违规次数超限，请联系教务 |
| `pending`              | 阅卷中/校验中  | 拒绝但可重试 | 资格校验中，请稍后重试       |
| `prerequisite_missing` | 前置课程未完成 | 拒绝         | 请先完成前置课程             |

**下游不要自己写第二套文案映射。** `reason` 是契约的一部分，两侧各写一套必然出现同一原因两种说法。

#### 8.3.3 超时与降级

| 情形                      | 返回                         | 不做的事                         |
| ------------------------- | ---------------------------- | -------------------------------- |
| 回源成功 `eligible=true`  | 允许报名                     | 不二次校验                       |
| 回源成功 `eligible=false` | 拒绝，`reason` 原样返回      | 不把 `failed` 改成 `not_started` |
| 回源超时                  | `pending`，HTTP 200          | **不判为不合格**                 |
| 回源 5xx                  | `pending`，HTTP 200          | 不重试超过 1 次                  |
| 回源 401/403              | `SERVICE_UNAVAILABLE` + 告警 | 不静默放行                       |

**超时不能当作"未完成"。** 把网络问题判成"你没通过考试"，用户会被无理由挡在项目外，且投诉时无法解释。`pending` 与 `prerequisite_missing` 必须是两个不同的 reason，前端文案也不同。

#### 8.3.4 缓存规则

| 项       | 值                                            | 理由                                     |
| -------- | --------------------------------------------- | ---------------------------------------- |
| 键       | `admission:{subject}:{courseId}`              | 与考试平台缓存键同构，便于对账           |
| TTL      | 60 秒                                         | 学生刚考完就来报名，等太久是最易投诉的点 |
| 投影 TTL | 5 分钟                                        | 快路径用，但不得作为拒绝依据             |
| 失效     | 收到 `exam.passed` / `exam.failed` 时主动刷新 | 事件到即更新，缩短不一致窗口             |
| 上限     | 禁止 > 30 分钟                                | 超过即视为设计错误                       |

### 8.4 事件封套与投递

#### 8.4.1 本期能力

| 项               | 状态 | 说明                                 |
| ---------------- | :--: | ------------------------------------ |
| 封套定义         |  ✓   | `event-envelope.yaml`                |
| 生产（本平台发） |  ×   | 无发件箱，本期不生产                 |
| 消费（本平台收） |  △   | 可接收，但没有投递器与重试，靠人工补 |
| 幂等表           |  ×   | 待建                                 |

**结论：本期不要设计"等事件到了才放行"的流程。** 事件链路不通，流程会挂住。准入一律走 8.3 的同步回源。

#### 8.4.2 封套字段（消费侧必须校验）

| 字段             | 必填 | 校验规则                                      |
| ---------------- | :--: | --------------------------------------------- |
| `eventId`        |  是  | 非空，全局唯一，用作幂等主键                  |
| `eventType`      |  是  | 必须在目录内（`exam.passed` / `exam.failed`） |
| `eventVersion`   |  是  | 当前只接受 `1.0`                              |
| `occurredAt`     |  是  | RFC 3339 UTC                                  |
| `sourcePlatform` |  是  | 必须是 `exam`                                 |
| `sourceEntityId` |  是  | 非空，如 `record_5001`                        |
| `actorId`        |  是  | 非空；系统操作为 `system`                     |
| `correlationId`  |  是  | 非空                                          |
| `requestId`      |  是  | 非空，用于串联                                |
| `data`           |  是  | 对象，含 `userId`、`examId`、`passed` 等      |

任一项不满足即**拒收并告警**，不要"尽力解析"。封套不完整的消息一旦入库，后续无法补救。

#### 8.4.3 事件到本地投影的映射

| 事件字段           | 落库位置                                                       |
| ------------------ | -------------------------------------------------------------- |
| `data.userId`      | `pre_exam_admission_projection.subject`                        |
| `data.courseId`    | `course_id`                                                    |
| `data.passed`      | `eligible`（1 / 0）                                            |
| `eventType`        | `reason`（`exam.passed` → `passed`，`exam.failed` → `failed`） |
| `data.score`       | `score`                                                        |
| `data.ruleVersion` | `rule_version`                                                 |
| `occurredAt`       | `granted_at`                                                   |
| `eventId`          | `last_event_id`（幂等用）                                      |

### 8.5 幂等消费

```sql
CREATE TABLE `pre_exam_event_inbox` (
  `event_id`        VARCHAR(64) NOT NULL COMMENT '全局唯一，主键去重',
  `event_type`      VARCHAR(64) NOT NULL,
  `source_platform` VARCHAR(32) NOT NULL,
  `occurred_at`     DATETIME    NOT NULL,
  `received_at`     DATETIME    NOT NULL,
  `status`          TINYINT     NOT NULL DEFAULT 1 COMMENT '1 已处理 2 处理失败',
  `last_error`      VARCHAR(500) NOT NULL DEFAULT '',
  PRIMARY KEY (`event_id`),
  KEY `idx_type_time` (`event_type`, `occurred_at`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='事件消费去重';
```

**`event_id` 做主键，不要用自增 + 唯一索引。** 主键去重能在插入阶段就拦掉重复；唯一索引要等事务提交才报错，中间业务逻辑已经执行了。

去重记录与业务效果必须**同一事务**提交。先写业务再写去重，中间崩溃会导致重放时重复生效。

### 8.6 数据级别与字段过滤

| 数据           | 级别 | 本平台处置                                                    |
| -------------- | ---- | ------------------------------------------------------------- |
| 试题与标准答案 | 机密 | **不接收、不存储、不展示**；接口不返回 `answer` 字段          |
| 考生作答       | 敏感 | 同上，本平台无作答数据                                        |
| 成绩           | 敏感 | 只读展示，本人可见；不落库，缓存不超过 60 秒                  |
| 防作弊记录     | 敏感 | 只接收计数（`violationCount`），不接收明细                    |
| 用户身份       | 内部 | 只存 `subject`、`realName`、`studentNo`，不存手机号与身份证号 |

**字段级过滤比接口级权限更可靠。** 学生查询招募详情时，服务端必须显式剔除不该给的字段，而不是依赖"前端不显示"。

### 8.7 六种不一致与处置

| 现象                       | 可能原因              | 处置                                            |
| -------------------------- | --------------------- | ----------------------------------------------- |
| 回源 404                   | `courseId` 形态不一致 | 以考试平台返回形态为准，本平台只存不改          |
| 回源 403                   | L2 凭证缺 scope       | 申请 `admission:read` 授权，不要绕过            |
| `eligible=true` 但成绩为 0 | 免考或跳级通过        | 以 `eligible` 为准，成绩仅展示                  |
| 两侧 `userId` 不同         | 一侧做了加工          | 排查加工点，恢复原值；脏数据按 `studentNo` 修正 |
| 事件到了但投影没更新       | 消费失败或未实现      | 查 inbox 表与投递日志，修好后重放               |
| 同一课程两条投影           | 重复投递或用户重考    | 以 `occurredAt` 较晚者为准，投影表建唯一索引    |

## 9 异常处理机制

### 9.1 异常分类

| 类别       | 举例                                   | 处理原则                         |
| ---------- | -------------------------------------- | -------------------------------- |
| 客户端错误 | 参数缺失、`pageSize` 超限、幂等键缺失  | 4xx，不重试，提示到字段          |
| 认证错误   | 无会话、会话过期、签名缺失             | 401/403，走重新登录              |
| 授权错误   | 权限点不足、资源不属于本人             | 403，不重试                      |
| 业务拒绝   | 已满员、已报名、状态不允许             | 200 + `BUSINESS_ERROR`，展示原因 |
| 依赖故障   | 身份中心不可用、考试平台超时、Redis 挂 | 5xx 或降级，可重试               |
| 平台故障   | 未捕获异常、数据库连接失败             | 500，带 `requestId` 反馈         |

**业务拒绝与系统错误必须区分。** "你已在队伍中"不是错误，是正常业务结果，用 200 + `BUSINESS_ERROR`。若用 500 返回，监控会误报。

### 9.2 错误响应形态

```json
{
  "ret": -1,
  "msg": "当前招募不可报名",
  "data": {},
  "code": "CONFLICT",
  "requestId": "req_9c2f1e8a4b7d3f60c1a5"
}
```

| 字段        | 规则                                                 |
| ----------- | ---------------------------------------------------- |
| `ret`       | 失败为 `-1`（未登录/业务拒绝）或 `0`（部分校验失败） |
| `msg`       | 面向用户的中文提示，不含堆栈、SQL、文件路径          |
| `data`      | 失败时返回 `{}` 或 `[]`，**不为 `null`**             |
| `code`      | 9 个规范码之一                                       |
| `requestId` | 必带，供用户反馈时提供给运维                         |

`data.reason` 用于携带机器可读的细分原因（如 `APP_CODE_INVALID`、`IDEMPOTENCY_KEY_MISSING`），前端据此做精确提示。

### 9.3 超时与重试矩阵

| 调用                      | 连接超时 | 总超时 |         重试         | 退避   |
| ------------------------- | :------: | :----: | :------------------: | ------ |
| 浏览器 → 网关             |   5 s    |  30 s  |       用户手动       | —      |
| 网关 → 本平台             |   3 s    |  30 s  | 否（写）/ 2 次（读） | 1s、3s |
| 本平台 → 身份中心（换码） |   1 s    |  3 s   |        **否**        | —      |
| 本平台 → 身份中心（自省） |  300 ms  | 800 ms |         1 次         | 200ms  |
| 本平台 → 考试平台（准入） |  500 ms  | 1.5 s  |         1 次         | 200ms  |
| 本平台 → Redis            |  200 ms  | 500 ms |          否          | —      |
| 本平台 → MySQL            |   1 s    |  3 s   |          否          | —      |

**换码请求永不重试。** `code` 一次性，重试必然失败，且第一次请求可能已在身份中心侧成功并吊销了 `code`。

**准入查询重试 1 次就够。** 两次都超时说明考试平台不可用，继续重试只会拖长用户等待。此时返回 `pending` 让用户稍后重试，比让他等 5 秒看到超时页体验更好。

### 9.4 降级与兜底

| 依赖故障       | 降级行为                                                  | 用户可见        |
| -------------- | --------------------------------------------------------- | --------------- |
| 身份中心不可用 | 已登录会话在 TTL 内继续可用；新登录提示"认证服务暂不可用" | 提示 + 重试按钮 |
| 考试平台不可用 | 准入返回 `pending`，允许用户稍后重试                      | "资格校验中"    |
| Redis 不可用   | 会话失效（无法降级）；准入缓存穿透到回源                  | 重新登录        |
| MySQL 不可用   | 返回 `SERVICE_UNAVAILABLE`，不返回部分数据                | 统一 503 页     |
| 事件代理不可用 | 不影响主流程（本期本就不消费事件）                        | 无感知          |

**不得降级为免登录。** 任何"认证服务挂了就先放人进来"的方案都不接受——这等于把整个权限体系作废。

### 9.5 死信与重放

本期本平台不生产事件，无死信。消费侧若落地投递器，按下列四态状态机设计：

| 状态        | 含义   | 进入条件                 |
| ----------- | ------ | ------------------------ |
| 0 `pending` | 待投递 | 业务事务内写入           |
| 1 `sent`    | 已投递 | 投递成功                 |
| 2 `failed`  | 待重试 | 失败且 `retryCount < 6`  |
| 3 `dead`    | 死信   | 失败且 `retryCount >= 6` |

| 次数 | 间隔    | 累计     | 动作             |
| ---- | ------- | -------- | ---------------- |
| 1    | 1 秒    | 1 秒     | 瞬时抖动         |
| 2    | 5 秒    | 6 秒     | —                |
| 3    | 30 秒   | 36 秒    | 计入告警指标     |
| 4    | 2 分钟  | ≈3 分钟  | —                |
| 5    | 10 分钟 | ≈13 分钟 | 通知集成负责人   |
| 6    | 1 小时  | ≈73 分钟 | 置 `dead` + 告警 |

**4xx 不重试。** 契约错误重试一百次也不会成功，应告警并人工修数据。

重放规则：把 `status` 改回 0、`retryCount` 清零、`nextRetryAt` 置 0，保留原 `eventId`。由授权人员执行，禁止批量无差别重置，每次记录操作人、时间、条数。消费方按 `eventId` 幂等，因此重放是安全的。

### 9.6 排障流程

```text
用户报错
  │
  ├─ 有 requestId？
  │    ├─ 有 → grep storage/logs/platform-access.log 中的 requestId
  │    │         └─ 看 status、duration、path、appCode
  │    │               ├─ status 5xx → 查 php-fpm 错误日志与 laravel.log
  │    │               ├─ status 4xx → 看 code 与 msg，定位契约/权限
  │    │               └─ 上游慢     → 看 duration，查 MySQL/Redis/外部调用
  │    └─ 无 → 按时间窗 + 用户 + IP 关联访问日志
  │
  ├─ 涉及跨平台
  │    └─ 用同一 requestId 去考试平台日志查（两侧透传该头）
  │
  └─ 涉及数据不一致
       └─ 对比两侧 userinfo 的 userId、投影表与回源结果
```

### 9.7 现象 → 原因 → 处置

| 现象                           | 常见原因                                                    | 处置                                        |
| ------------------------------ | ----------------------------------------------------------- | ------------------------------------------- |
| 返回 HTML 而不是 JSON          | 缺 `Content-Type: application/json`，或路径写错命中页面路由 | 补齐头；核对路径前缀                        |
| `code=OK` 但业务没生效         | 看的是 `ret`，读错了字段                                    | 以 `code` 判成功                            |
| 200 + `FORBIDDEN`              | 存量接口未统一状态码                                        | 按 6.5 统一；接入方先判 `code` 再判 HTTP    |
| 方法名写错返回 200             | 派发器把未找到包装成 `NOT_FOUND` 文本                       | 核对 `openapi.yaml` 的 path                 |
| `AUTH_REQUIRED` 但用户说已登录 | 凭证未带 / 会话过期 / 签名缺失                              | 查请求头 `Cookie` 与 `X-Internal-Sign`      |
| 用户被拦"未通过考试"但考试已过 | 回源超时被误判，或 `courseId` 形态不一致                    | 查 reason 是否为 `pending`；比对 `courseId` |
| 同一用户两次报名得到两条记录   | 幂等键缺失 + 并发                                           | 补 `Idempotency-Key`，唯一索引兜底          |
| `requestId` 在响应体中缺失     | 响应不是 JSON 对象或体积 > 2 MB                             | 查中间件跳过条件                            |
| 直连上游能改数据               | 安全组放行过宽 + 未验签                                     | 收紧网段 + 开启 `X-Internal-Sign` 校验      |

```text
 │               │                  │                              │ 查准入
 │               │                  │◄─────────────────────────────┤
 │               │                  │ {eligible, reason, score}    │
 │               │                  │ 4. eligible=false → 拒绝     │
 │               │                  │ 5. 写报名记录 + 刷新投影     │
 │               │◄─────────────────┤                              │
 │◄──────────────┤  200 / 业务拒绝  │                              │
```

**校验插在原有前置校验之后。** 先判"招募是否可报名、是否已截止、是否已在队中"，这些是零成本的本地判断；再去回源。顺序反了会让每个无效请求都打一次考试平台。

#### 10.3.2 超时分支

```text
本平台                         考试平台
  │                              │
  ├──── GET /admissions ────────►│
  │         (1.5s 超时)          │
  │                              │
  │  ✗ 超时                      │
  │                              │
  ├─ 返回 200, code=OK           │
  │  data: {eligible: false,     │
  │         reason: "pending"}   │
  │                              │
  └─ 不写报名记录，不缓存失败结论 │
```

**超时结论不写入缓存。** 把 `pending` 缓存 60 秒会让用户在考试平台恢复后仍被挡一分钟。只缓存明确的 `eligible` 结论。

### 10.4 本地落库

#### 10.4.1 准入投影表

```sql
CREATE TABLE `pre_exam_admission_projection` (
  `id`            BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
  `subject`       VARCHAR(64)  NOT NULL COMMENT '论坛 sub 原值',
  `course_id`     VARCHAR(64)  NOT NULL COMMENT '课程ID，原值存储',
  `eligible`      TINYINT      NOT NULL DEFAULT 0 COMMENT '1 通过 0 未通过',
  `reason`        VARCHAR(32)  NOT NULL DEFAULT '' COMMENT '对齐考试平台 reason 枚举',
  `score`         INT          NULL COMMENT '成绩，仅展示',
  `rule_version`  VARCHAR(32)  NOT NULL DEFAULT '' COMMENT '规则版本',
  `granted_at`    DATETIME     NULL COMMENT '结论时间（UTC）',
  `source`        TINYINT      NOT NULL DEFAULT 1 COMMENT '1 回源 2 事件',
  `last_event_id` VARCHAR(64)  NOT NULL DEFAULT '' COMMENT '最近生效的 eventId',
  `expires_at`    DATETIME     NOT NULL COMMENT '本地缓存过期时间',
  `created_at`    DATETIME     NOT NULL,
  `updated_at`    DATETIME     NOT NULL,
  PRIMARY KEY (`id`),
  UNIQUE KEY `uk_subject_course` (`subject`, `course_id`),
  KEY `idx_expires` (`expires_at`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='考试准入投影（只加速，不拒绝）';
```

**唯一索引 `(subject, course_id)` 是必须的。** 同一课程重复投递或用户重考，靠它保证只有一行，以 `granted_at` 较晚者为准。

**`expires_at` 到点即失效。** 查询时判断 `expires_at > NOW()`，过期视为未命中，走回源。

#### 10.4.2 招募表新增字段

```sql
ALTER TABLE `pre_project_recruitments`
  ADD COLUMN `course_id` VARCHAR(64) NOT NULL DEFAULT ''
  COMMENT '关联课程ID；空表示不校验考试准入' AFTER `project_id`;
```

`course_id` 为空时，报名流程与改造前完全一致——这是保证存量功能不受影响的开关。

### 10.5 事件消费

#### 10.5.1 消费逻辑

```text
收到事件
  │
  ├─ 校验封套 10 个必填字段（8.4.2）── 缺一即拒收 + 告警
  │
  ├─ 查 pre_exam_event_inbox(event_id)
  │     └─ 已存在 ──► 直接返回成功（幂等）
  │
  ├─ 开事务
  │    ├─ insert inbox(event_id, status=1)
  │    ├─ upsert 投影表（冲突时取 occurredAt 较晚者）
  │    └─ commit
  │
  └─ 任何异常 ──► 回滚，inbox 记录为 status=2，交重试
```

#### 10.5.2 与准入缓存的关系

事件到达后：

1. 更新投影表；
2. `DEL admission:{subject}:{courseId}`，让下一次查询走回源；
3. 不主动推送给前端（无长连接），用户下次刷新即可看到。

**不要用事件直接覆盖用户界面状态。** 事件是最终一致的，界面状态以查询为准。

### 10.6 联调十步检查单

| #   | 操作                                                                 | 预期结果                                                    | 失败排查方向                              |
| --- | -------------------------------------------------------------------- | ----------------------------------------------------------- | ----------------------------------------- |
| 1   | `curl https://auth.jingyuan.edu.cn/.well-known/openid-configuration` | 返回 JSON，`issuer` 与配置一致，含 `introspection_endpoint` | 缺自省端点 → 走 Q2 结论                   |
| 2   | 访问 `/api/v1/workshop/auth/login`                                   | 302 到身份中心，`Location` 含 `state` 与 `code_challenge`   | 缺 PKCE → 检查 verifier 生成              |
| 3   | 完成登录并回跳                                                       | 落到回调后 302 回原页面；浏览器仅有 `__Host-workshop_sid`   | `state` 不匹配 → 查 SameSite 与 Cookie 域 |
| 4   | DevTools 查 localStorage / sessionStorage                            | 无任何 token                                                | 仍有 → 前端令牌层未下线                   |
| 5   | `GET /api/v1/workshop/auth/userinfo`                                 | `code=OK`，`data.userId` 与考试平台逐字符相同               | 是数字 → 仍在用 `userid`                  |
| 6   | 清 Cookie 后调业务接口                                               | 401 `AUTH_REQUIRED`，响应含 `requestId`                     | 返回 200 → 免登录未关闭                   |
| 7   | 直连上游并伪造 `X-User-Id`                                           | 403 `FORBIDDEN`，日志标记 `direct_access`                   | 放行 → 验签未启用                         |
| 8   | 学生账号访问他人项目、调用管理员接口                                 | 403 或查不到；界面展示统一 403 页                           | 200 → 数据归属校验缺失                    |
| 9   | 同一 `Idempotency-Key` 连续两次报名                                  | 两次响应一致，报名表仅一条记录                              | 两条 → 幂等未落库                         |
| 10  | 学生考完试 → 查准入（先断开事件）                                    | `eligible=true`（回源生效）                                 | 依赖投影 → 未实现回源                     |

第 10 步必须**在事件通道断开的状态下**执行。如果事件通着测，通过可能是投影命中，回源根本没被验证。

### 10.8 回滚方案

| 场景           | 回滚动作                                                  | 影响与时限                  |
| -------------- | --------------------------------------------------------- | --------------------------- |
| 身份中心故障   | 已登录会话在 TTL 内继续可用；新登录提示"认证服务暂不可用" | ≤ 30 分钟；不得降级为免登录 |
| 网关故障       | 切备用网关；无备用时平台不直接暴露公网                    | 不可用直至恢复              |
| 考试平台不可用 | 准入返回 `pending`；`course_id` 全置空可临时绕过准入      | 无数据损失                  |
| 新版接口异常   | 路由开关切回旧 RPC 前缀                                   | ≤ 5 分钟                    |
| 事件消费异常   | 不影响主流程（准入走回源）；修复后重放                    | 数据不丢                    |
| 密钥轮换出错   | 双密钥并行窗口内回退旧密钥                                | ≤ 7 天窗口                  |

**`course_id` 置空是最后手段。** 它会让所有招募都不校验准入，等于临时关闭对接。只能由架构负责人在考试平台故障且影响面大时批准，事后必须恢复并复核已放行的报名。

## 12 场景示例

### 12.1 登录并拿到可用身份

**改造前（可直接复现）：**

```bash
curl -s --noproxy '*' -X POST http://127.0.0.1:2222/api/users/login \
  -H 'Content-Type: application/json' \
  -d '{"email":"tea-001@example.com","password":"******"}'
```

```json
{
  "ret": 1,
  "msg": "登录成功",
  "data": { "token": "MTAyMzEjIy4uLg==", "user": { "userid": 10231 } },
  "code": "OK",
  "requestId": "req_7f3c9a2e5b1d4c80a9f2"
}
```

**改造后：**

```text
1. 浏览器 → GET /api/v1/workshop/auth/login?redirect=/project
2. 302 → 身份中心授权页
3. 回调 → GET /api/v1/workshop/auth/oauth/callback?code=...&state=...
4. 服务端换码 → 建会话 → Set-Cookie: __Host-workshop_sid=...; HttpOnly; Secure; SameSite=Lax
5. 302 → /project
```

`data` 中**不再出现 token**。这是判定改造是否彻底的第一条硬标准。

### 12.2 读取当前用户的项目列表

```bash
curl -s --noproxy '*' "http://127.0.0.1:2222/api/project/lists?page=1&pagesize=20" \
  -H 'token: <凭证>' \
  -H 'X-App-Code: workshop' \
  -H 'X-Request-Id: trace-abc-0001'
```

```json
{
  "ret": 1,
  "msg": "success",
  "data": {
    "lists": [{ "project_id": 12, "name": "智慧校园巡检", "owner": 10231 }],
    "total": 1,
    "page": 1,
    "pagesize": 20
  },
  "code": "OK",
  "requestId": "trace-abc-0001"
}
```

要点：

- `X-Request-Id` 合法（8–128 位 `[A-Za-z0-9._:-]`）时**原样沿用**，非法或缺省时回落为 `req_<20位十六进制>`；
- 列表自动附加「我是成员」条件，非成员的项目不会出现，不是分页问题；
- 返回的 `userid` 是本地主键，**不要**拿它去跨平台查询。

### 12.3 带准入校验的报名（核心场景）

```bash
curl -s --noproxy '*' -X POST "http://127.0.0.1:2222/api/recruitment/apply" \
  -H 'Content-Type: application/json' \
  -H 'token: <凭证>' \
  -H 'X-App-Code: workshop' \
  -H 'Idempotency-Key: 6f1c9b2e-3a4d-4e5f-8b7a-1c2d3e4f5a6b' \
  -d '{"recruitment_id": 88, "message": "希望加入"}'
```

内部执行：

```text
1. 幂等键检查（命中即返回缓存结果）
2. 招募存在、状态 recruiting、未截止、非发布者本人、未在队中、未重复报名
3. 招募 course_id = "course_9" → 查缓存
4. 未命中 → GET /api/v1/exam/admissions/usr_01J8ZQ7M2K/course_9（1.5s 超时）
5. eligible=true → 写报名记录 + 刷新投影
```

成功：

```json
{
  "ret": 1,
  "msg": "报名成功",
  "data": { "id": 501, "status": "pending", "admission": { "eligible": true, "reason": "passed" } },
  "code": "OK",
  "requestId": "req_8a1f..."
}
```

准入未通过：

```json
{
  "ret": -1,
  "msg": "考试成绩未达标，请重新考试",
  "data": { "admission": { "eligible": false, "reason": "failed", "score": 52 } },
  "code": "BUSINESS_ERROR",
  "requestId": "req_8a1f..."
}
```

回源超时（**注意不是拒绝**）：

```json
{
  "ret": -1,
  "msg": "资格校验中，请稍后重试",
  "data": { "admission": { "eligible": false, "reason": "pending" } },
  "code": "BUSINESS_ERROR",
  "requestId": "req_8a1f..."
}
```

前端对 `pending` 必须展示"重试"按钮，对 `failed` 展示"去考试"入口。两者文案不同，不能合并成一句"报名失败"。

### 12.4 跨平台调用（带来源标识与 L2 签名）

本平台调考试平台：

```bash
TS=$(date +%s)
NONCE=$(openssl rand -hex 8)
BODY=''
# 规范化串：method \n path \n query \n body
SIGN=$(printf 'GET\n/api/v1/exam/admissions/usr_01J8ZQ7M2K/course_9\n\n%s' "$BODY" \
  | openssl dgst -sha256 -hmac "$EXAM_APP_SECRET" -hex | awk '{print $2}')

curl -s "https://api.jingyuan.edu.cn/api/v1/exam/admissions/usr_01J8ZQ7M2K/course_9" \
  -H "X-App-Key: svc-workshop" \
  -H "X-Timestamp: $TS" \
  -H "X-Nonce: $NONCE" \
  -H "X-Sign-Alg: HMAC-SHA256" \
  -H "X-Signature: $SIGN" \
  -H 'X-App-Code: workshop'
```

要点：

- 时间窗 ±300 秒，机器必须启用 NTP；
- `X-Nonce` 在窗口内不得重复，网关会做重放检测；
- 签名覆盖 `method`、`path`、`query`、`body` 四段，顺序不可调整；
- **L2 凭证不得下发给前端**，它能让调用方代表"实训平台"这个系统行事。

### 12.5 文件上传

```bash
curl -s --noproxy '*' -X POST "http://127.0.0.1:2222/api/file/add" \
  -H 'token: <凭证>' \
  -H 'X-App-Code: workshop' \
  -F 'file=@./design.pdf' \
  -F 'project_id=12'
```

| 项   | 说明                                                          |
| ---- | ------------------------------------------------------------- |
| 编码 | `multipart/form-data`（不是 JSON）                            |
| 体积 | 单文件上限由 nginx `client_max_body_size` 控制，网关侧 50 MB  |
| 响应 | 与其他接口同构，含 `code` 与 `requestId`                      |
| 注意 | `/api/file/content/upload` 不在契约内，接入方须书面确认后再用 |

### 12.6 统一状态页

改造后前端必须有五态，缺一会导致"白屏"或"转圈不停"：

| 状态    | 触发                                | 展示                                   |
| ------- | ----------------------------------- | -------------------------------------- |
| 加载中  | 请求未返回                          | 骨架屏；超过 3 秒追加"加载较慢"提示    |
| 空数据  | `data.lists` 为空                   | 空状态插图 + 下一步动作                |
| 错误    | `code != OK` 且非鉴权类             | 错误说明 + `requestId` + 重试按钮      |
| 403     | `code=FORBIDDEN`                    | 统一无权限页，不带"返回上一页"的死循环 |
| 404/503 | `NOT_FOUND` / `SERVICE_UNAVAILABLE` | 统一页 + 重试；503 时提示"稍后重试"    |

**错误页必须显示 `requestId`。** 用户报障时提供这个值，运维能直接定位到那一次请求，省掉"大概几点、什么操作"的来回。

| DV-12 | `AUTH_TOKEN_EXPIRED` 无产出点              | 枚举与实际不符               | 6.5.1 明确说明，接入方不写该分支           |
| DV-13 | 分页默认值按接口不同                       | 易误用                       | 6.6 逐接口列明                             |
| DV-14 | `/api/file/content/upload` 未入契约        | 存在但无定义                 | 6.2 标注，须书面确认                       |
| DV-15 | `pre_project_logs` 缺 `requestId`          | 业务日志无法与访问日志关联   | G15，本期补列                              |
| DV-16 | 无 `sub` 字段，主键为自增                  | 跨平台无法直接对齐           | 4.1 绑定表                                 |

## 附录 B 联调命令集

```bash
# 1 校验 Discovery
curl -s https://auth.jingyuan.edu.cn/.well-known/openid-configuration \
  | jq '.issuer,.authorization_endpoint,.token_endpoint,.introspection_endpoint'

# 2 未登录访问业务接口（期望 401 / AUTH_REQUIRED）
curl -s -i http://127.0.0.1:2222/api/project/lists | head -20

# 3 信封与 requestId 回带
curl -s -D - -H 'x-request-id: trace-abc-0001' \
  http://127.0.0.1:2222/api/system/setting
#    期望：响应头 X-Request-Id: trace-abc-0001；响应体含 "code":"OK","requestId":"trace-abc-0001"

# 4 非法平台编码（期望 400 / VALIDATION_ERROR / APP_CODE_INVALID）
curl -s -H 'x-app-code: hacker' http://127.0.0.1:2222/api/system/setting

# 5 伪造身份头直连上游（期望 403 / FORBIDDEN）
curl -s -i -H 'X-User-Id: usr_fake' -H 'X-Auth-Mode: user' \
  http://127.0.0.1:8000/api/v1/workshop/projects

# 6 报名幂等：同一 key 提交两次，报名表应只有一条
KEY=$(uuidgen)
for i in 1 2; do
  curl -s -X POST http://127.0.0.1:2222/api/recruitment/apply \
       -H 'Content-Type: application/json' \
       -H "Idempotency-Key: $KEY" \
       -H 'token: <凭证>' \
       -d '{"recruitment_id":88,"message":"test"}' | jq '.code,.data.id'
done

# 7 回源考试平台（L2 签名）
curl -s -H "X-App-Key: svc-workshop" -H "X-Timestamp: $(date +%s)" \
     -H 'X-Nonce: 8f3c9a2e' -H 'X-Sign-Alg: HMAC-SHA256' \
     -H 'X-Signature: <hex>' \
     'https://api.jingyuan.edu.cn/api/v1/exam/admissions/usr_01J8ZQ7M2K/course_9' \
  | jq '.code,.data.eligible,.data.reason'

# 8 访问日志
tail -n 3 storage/logs/platform-access.log | jq -c '{requestId,path,status,duration}'

# 9 契约对账（改错方法名会失败）
npm run typecheck

# 10 全量门禁
PHP_BIN=D:/dt-run/php/php.exe npm run check
```

Windows Git Bash 下 `curl` 必须加 `--noproxy '*'`，否则请求会被系统代理拦成 502。
